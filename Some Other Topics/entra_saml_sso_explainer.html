SAML-based SSO in Entra ID — Detailed explainer for each section

SAML 2.0 is a federation protocol. Entra ID acts as the Identity Provider (IdP) and SAP Analytics Cloud is the Service Provider (SP). The user proves their identity once to Entra ID, which issues a signed XML assertion that SAP trusts.
SP-initiated flow (most common)
1
User visits SAP Analytics Cloud
No session exists. SAP detects the user isn't logged in.
2
SAP generates a SAML AuthnRequest
An XML document is created and signed, then Base64-encoded. It's sent to the browser as a redirect to Entra ID's SSO URL (Login URL).
GET https://login.microsoftonline.com/<tenantId>/saml2?SAMLRequest=PD94...
3
Entra ID authenticates the user
Full authentication occurs — password, MFA, Conditional Access policies are all evaluated here. The user never re-enters credentials on the SAP side.
4
Entra ID posts a SAML Response to SAP's ACS URL
An HTTP POST is sent to SAP's Assertion Consumer Service (ACS) URL containing a signed XML SAML Response with the assertion (user attributes inside).
POST https://<sap-domain>/saml/acs Body: SAMLResponse=PHNhbWxw...
5
SAP validates the assertion
SAP uses Entra ID's public certificate (from step ③) to verify the XML signature. If valid, it extracts attributes like email, name, and creates the user session.
6
User is logged in to SAP
The user sees their SAP Analytics Cloud dashboard with no additional sign-in required. The session is governed by SAP's own session timeout settings.
IdP-initiated flow
1
User starts from the MyApps portal or an app tile
Entra ID directly generates and posts a SAML assertion to SAP's ACS URL without SAP sending an AuthnRequest first. No prior visit to SAP is needed.
2
SAP validates and creates the session
Same as steps 5–6 above. The Relay State field can tell SAP which page to redirect to after login.

Relay State Optional
Passed through the SAML flow and returned to SAP. SAP can use it to redirect users to a specific page or dashboard after login (deep linking). Leave blank if not needed.
Logout URL Optional
SAP's Single Logout (SLO) endpoint. When the user signs out of Entra ID (e.g. via MyApps), Entra ID will POST a LogoutRequest here so SAP also terminates its session. Without this, signing out of Entra ID won't log the user out of SAP.
Typical formathttps://<sap-tenant>/saml/slo
Claims are key-value pairs included inside the SAML assertion XML. SAP reads these to identify the user and (optionally) provision attributes like role, department, or cost center. The Unique User Identifier is the most critical — it must match the user identity in SAP.

What each Entra ID source means
user.userprincipalnameThe user's UPN — e.g. alice@contoso.com. Most reliable for cloud-only accounts.
user.mailThe user's primary email address (can differ from UPN in hybrid setups).
user.givennameFirst name attribute from the Entra ID user object.
user.onpremisessamaccountnameUseful for hybrid environments where SAP uses Windows AD usernames for matching.
user.objectidThe Entra ID GUID — immutable even if UPN or email changes. Best for long-term stability.
Common issue: If SAP can't find the user after SAML login, the Unique User Identifier claim doesn't match how users are stored in SAP. Compare the claim value in the raw SAML response (use browser dev tools → Network tab) with the user ID format in SAP's user management.

The certificate is how SAP knows a SAML assertion actually came from Entra ID. Entra ID signs the XML with its private key, and SAP verifies the signature using Entra ID's public certificate. Without this, anyone could forge a SAML assertion and log in as any user.

Certificate expiry is a major outage risk. When the cert expires, ALL SAML logins fail instantly. Set the notification email and plan a rollover 30+ days before expiry. Entra ID supports rolling certs — make the new cert active before removing the old one.

SAP-side steps (after entering the above)
1
Upload Entra ID's certificate into SAP
In SAP Analytics Cloud → Security → SAML Identity Provider, upload the Base64 cert downloaded from Step ③.
2
Set the NameID mapping in SAP
Tell SAP which attribute to use as the user key — must match the Unique User Identifier claim set in Step ②.
3
Assign users in Entra ID
Go to Users and groups in the left nav and assign users or groups. Only assigned users can authenticate via SAML.
The Test button is greyed out until Step ①'s required fields (Entity ID, ACS URL, Sign on URL) are filled in.
What the Test button does
It simulates an SP-initiated login by opening the Sign on URL and redirecting through Entra ID authentication. If the full flow succeeds, you see a "Testing complete" confirmation. If it fails, a detailed error shows the SAML error code and step.
Common test failures and fixes
AADSTS50011 — reply URL mismatchACS URL in Entra ID doesn't exactly match what SAP is sending in the AuthnRequest.
AADSTS650056 — misconfigured appPermissions not granted. An admin must grant consent.
InvalidNameIDPolicySAP is requesting a NameID format that Entra ID isn't configured to send.
SAP error after redirectUser exists in Entra ID but not in SAP, or the Unique User Identifier doesn't match SAP's user store.
Debugging with the browser
1
Install SAML-tracer browser extension
Available for Chrome and Firefox. Captures and decodes the base64 SAML Request and Response in plaintext XML.
2
Trigger the login flow
Reproduce the error with the tracer active. You'll see the full AuthnRequest and Response XML, including all claims and the Issuer value.
3
Check Entra ID Sign-in logs
In Entra ID → Monitoring → Sign-in logs, filter by the SAP application. Failures show the exact error code and what condition triggered it.
How to change the mode: "Change single sign-on mode" in the top bar
Disabled
Default for new apps
SSO is turned off. Users cannot sign in via Entra ID. The app tile in MyApps still appears but clicking it does nothing. Use this during setup before configuration is complete.
SAML-based SSO
Current mode
Full federation using SAML 2.0 protocol. Entra ID is the IdP. Best for enterprise apps like SAP, Salesforce, ServiceNow. Supports MFA, Conditional Access, and detailed sign-in logs.
OpenID Connect / OAuth 2.0
Modern protocol
Token-based SSO using OIDC/OAuth. The app receives an ID token (JWT) instead of a SAML XML assertion. Used by modern cloud-native apps. Returns JSON, not XML. SAP Analytics Cloud also supports this.
Password-based SSO
Legacy / weak
Entra ID stores the app's username & password and auto-fills them via a browser extension. No real federation — Entra ID is just a password manager. Use only for legacy apps with no federation support.
Linked
Not real SSO
No authentication happens via Entra ID. The app tile in MyApps just navigates to the URL you configure. Useful for surfacing external URLs or apps already using a different IdP in the same app launcher. Entra ID does zero token issuance.
Integrated Windows Auth (IWA)
On-prem / hybrid
For on-premises apps published via Entra Application Proxy. Uses Kerberos Constrained Delegation (KCD) to give users seamless SSO to internal IIS/Windows apps without a VPN. Requires the App Proxy connector.
Header-based SSO
Legacy apps
Works with Application Proxy. Entra ID authenticates the user, then injects HTTP headers (X-Username, X-Email, etc.) into the proxied request. The app reads these headers instead of performing its own login. Common for Unix/Linux web apps.
When to use Linked: Your app is already federated with a different IdP (e.g. Okta or ADFS), but you want users to find it in the Entra ID / MyApps portal. Linked gives it an app tile without interfering with the existing federation.
